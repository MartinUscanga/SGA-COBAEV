# Multi-student portal for parent/tutor accounts

A tutor who has multiple children at the school can now see attendance data for all of them from a single login. The implementation adds a second query at login time that finds every `tutores` row sharing the same `nombre_tutor` + `password_tutor` pair, stores the resulting array in the session, and exposes pill-style tabs in padres.php to switch the active student. The FCM token registration and logout flows were widened to iterate over the full set of matriculas. A self-service "vincular alumno" form in perfil_tutor.php lets a tutor attach additional children post-login.

Watch for: any authenticated tutor can link any matricula in the `alumnos` table to their account without verification (confirmed); tutor identity is defined solely by a shared plaintext password, creating collision risk (confirmed); logout DELETEs all FCM rows for the tutor's students, which nukes registrations from other devices (confirmed).

## High-level view

The tutor identity model rests on an unusual foundation: two tutors are "the same person" if they share an identical `nombre_tutor` and `password_tutor`. A password collision between unrelated tutors silently merges their student lists. The model works for a small school with admin-controlled passwords, but breaks down as the user base grows or if tutors choose their own passwords.

The student-linking endpoint (`vincular_alumno` in perfil_tutor.php) verifies only that the matricula exists in the `alumnos` table. There is no proof-of-relationship check—no confirmation code, no admin approval. Any authenticated tutor can bind any student to their account and begin receiving that child's attendance notifications.

FCM token lifecycle has a semantic mismatch: login registers a device token for all students, but logout DELETEs every `dispositivos_padres` row for those students regardless of which device triggered the logout. A tutor logged into two devices who logs out of one will lose push notifications on the other.

The password change and data update operations broadcast across all `tutores` rows matching the name+password pair, amplifying the collision risk—changing a password for one tutor could accidentally update an unrelated tutor's row if the name+password happened to match.

<summary>Issues (5)</summary>

1. **Unguarded student linking** — Any authenticated tutor can link any valid matricula to their account via `vincular_alumno`. Add a verification step (e.g., a code issued by the school) before inserting the new `tutores` row.
2. **Tutor identity collision via password** — Tutor grouping relies on `nombre_tutor + password_tutor` equality. Two unrelated parents with the same name and the default `padre123` password would share student lists. Use a dedicated `tutor_id` or family group column instead.
3. **Logout deletes all device tokens** — `logout.php` DELETEs every `dispositivos_padres` row for the tutor's students, killing push on other devices. Delete only the current device's token (pass the FCM token from the client to identify which row to remove).
4. **Plaintext password storage and comparison** — Passwords are stored and compared in plain text (`$password_tutor === $tutor['password_tutor']`). Use `password_hash` / `password_verify`. This also makes the "same password = same tutor" grouping strategy more dangerous because collisions are trivially observable.
5. **Active-student switch via unsigned GET parameter** — `padres.php` changes the active student based on `$_GET['alumno']`, validated only against the session array. The session array itself can be poisoned via issue #1, widening what the GET switch exposes.

## Tutor identity model and login flow

`login_padres.php` authenticates with a single matricula, then discovers siblings by querying all `tutores` rows where `nombre_tutor = :nombre_tutor AND password_tutor = :password_tutor`. The assumption is that identical credentials imply the same human. In a fresh install where every tutor has `padre123`, this would merge all tutors named "Juan Perez" into one account.

## Authorization gap in student linking

```php
// perfil_tutor.php — vincular_alumno action
$check_alumno = $pdo->prepare("SELECT matricula, nombre, ... FROM alumnos WHERE matricula = :matricula");
```

The only check is that the matricula exists in the `alumnos` table. After that, a new row is inserted into `tutores` with the current tutor's name, phone, and password. There is no admin approval, no CURP match, no confirmation code sent to the student's existing tutor. Tutor A can link Student B (another family's child) and start receiving their attendance push notifications.

The session is updated immediately (`$_SESSION['alumnos'][] = ...`), so the new student's attendance becomes visible without re-login.

## FCM token registration and logout asymmetry

On login, `app.js` sends the full `MATRICULAS_USUARIO` array to `guardar_token.php`, which iterates and creates/updates one `dispositivos_padres` row per matricula. On logout, `logout.php` iterates `$_SESSION['alumnos']` and issues:

```php
DELETE FROM dispositivos_padres WHERE matricula_alumno = :matricula
```

This removes every row for each student regardless of which device's token it holds. If the tutor is logged in on a phone and a tablet, logging out on the phone deletes the tablet's FCM registration too. The fix is to delete only the row matching the current device's token:

```sql
DELETE FROM dispositivos_padres WHERE matricula_alumno = :matricula AND token_fcm = :token
```

This requires passing the token from the client to the logout endpoint (or storing it in the session at registration time).

## Password update blast radius

```php
// perfil_tutor.php — cambiar_password
UPDATE tutores SET password_tutor = :password_nueva 
WHERE nombre_tutor = :nombre_tutor AND password_tutor = :password_actual
```

This updates every row in `tutores` that matches the current name and password. Under the collision scenario (two unrelated tutors sharing credentials), changing a password affects both humans' accounts. The same pattern applies to the data-update action (name + phone).

## Plaintext credentials as a structural constraint

Both `login_padres.php` and `perfil_tutor.php` compare and store passwords in plain text. The multi-student grouping strategy makes this load-bearing: if passwords were hashed, the grouping query (`WHERE password_tutor = :password_tutor`) would fail because each hash is unique. Migrating to `password_hash` therefore requires a different grouping mechanism (e.g., a shared `familia_id` column).
