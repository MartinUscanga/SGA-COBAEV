# Admin dashboard for SGA COBAEV attendance system

Six PHP pages implementing a full administration panel (dashboard stats, student CRUD, tutor CRUD, attendance history, user management, FCM device viewer) behind session authentication. The pages follow the project's existing visual design system (Tailwind CDN, crema/vino/dorado palette) and share a duplicated sidebar/header layout. The approach is straightforward server-rendered PHP with PDO prepared statements — no framework, no AJAX, full page reloads for every action.

Watch for: plaintext passwords stored and compared without hashing across all CRUD pages (confirmed); SQL injection vector via LIMIT/OFFSET interpolation in multiple files (confirmed); missing CSRF protection on all destructive POST actions (confirmed); N+1 query pattern on the alumnos page that will degrade at scale (confirmed).

## High-level view

The authentication gate is consistent across all six files — a session boolean check redirecting to `login_admin.php` — but there is no role-based access control. Any authenticated user (Admin, Prefecto, Vigilante) can create, edit, or delete any record including other users. The `usuarios.php` page does prevent self-deletion but doesn't restrict lower-privilege roles from escalating.

All CRUD forms submit via plain POST without CSRF tokens. Since sessions are cookie-based and same-site is not explicitly set, a cross-origin form submission could trigger any administrative action (delete student, create admin user, send push notification) as long as the victim has an active session.

Passwords for tutors and system users are stored, compared, and displayed in plaintext. The admin panel creates new tutor and user records with raw strings in the database. The tutor password field uses `type="text"` in the form, making it visible on screen and in browser history.

The query construction pattern for paginated lists interpolates `$por_pagina` and `$offset` directly into SQL strings rather than binding them as parameters. While both values pass through `max(1, (int)...)` coercion, this establishes a fragile pattern — any future change that alters the coercion could open a SQL injection path. The `match()` syntax in `usuarios.php` also requires PHP 8.0+.

The `dispositivos_padres` table referenced in `dispositivos.php` and the `usuarios` table referenced in `usuarios.php` are both absent from `database_structure.sql`. Anyone setting up a fresh environment from the schema file will get immediate fatal errors on these two pages.

The dashboard's "en plantel" query uses a correlated NOT EXISTS subquery that will scan the entire day's attendance records for every student. This design works with tens of students but will become a performance bottleneck at school scale (hundreds of students, thousands of daily records).

<summary>Issues (8)</summary>

1. **Plaintext password storage** — All password fields (tutor and user) are stored and compared as raw strings. Use `password_hash()` on write and `password_verify()` on read.
2. **No CSRF protection** — Every POST form (create, edit, delete, send notification) lacks a token. Add a session-based CSRF token to all forms.
3. **SQL interpolation in LIMIT/OFFSET** — `$por_pagina` and `$offset` are string-interpolated into queries in alumnos.php, tutores.php, asistencias.php, and dispositivos.php. Bind them as integer parameters or keep the cast-then-interpolate pattern but document the invariant.
4. **No role-based authorization** — Any authenticated user can access all admin pages and perform all operations. Add role checks to restrict destructive actions to Admin role.
5. **Missing tables in schema** — `usuarios` and `dispositivos_padres` are not defined in `database_structure.sql`. Add their CREATE TABLE statements.
6. **N+1 query in alumnos.php** — Each student triggers a separate query to check today's attendance status. Replace with a single LEFT JOIN subquery.
7. **Tutor password visible in form** — The password field in `tutores.php` uses `type="text"`, exposing credentials on screen.
8. **PHP 8.0 dependency** — `match()` expression in `usuarios.php` fails on PHP 7.x. Document the minimum version or replace with a switch.

## Plaintext credential handling across CRUD pages

The `tutores.php` create action inserts `trim($_POST['password_tutor'])` directly into the database. The edit path conditionally updates the same field if non-empty. The form renders the password input with `type="text"`, so it's visible on screen and captured in browser autocomplete history. The `usuarios.php` page follows the same pattern for `password_admin`. Given that `login_admin.php` already compares `$password === $user['password_admin']` (plaintext), this is a system-wide design rather than an oversight — but the admin panel now amplifies the risk by giving any admin the ability to read and set other users' passwords without hashing.

The `login_padres.php` comment acknowledges this trade-off ("para tu XAMPP local esto jala perfecto"), but as an admin dashboard that manages all users and tutors at once, shipping without hashing means anyone with read access to the database (or a SQL injection elsewhere) gets every credential.

## CSRF-vulnerable destructive actions

Every form across all six files submits via POST to the same page without a nonce or token. The delete operations in `alumnos.php`, `tutores.php`, `usuarios.php`, and `dispositivos.php` are especially dangerous: an attacker who knows a student's matricula can craft a form that soft-deletes the record. The "send test notification" action in `dispositivos.php` is also unprotected, meaning a CSRF could trigger push notifications to arbitrary parents.

The fix is a per-session token stored in `$_SESSION['csrf_token']` and validated against a hidden input on every POST. Since these pages already call `session_start()`, the infrastructure is in place.

## SQL interpolation pattern in paginated queries

In `alumnos.php`:
```php
$stmt = $pdo->prepare("SELECT * FROM alumnos $where ORDER BY apellido_paterno, nombre LIMIT $por_pagina OFFSET $offset");
```

The same pattern appears in `tutores.php`, `asistencias.php`, and `dispositivos.php`. The values are safe today because they pass through `(int)` casts, but PDO supports integer-bound LIMIT/OFFSET (with `PDO::PARAM_INT` and emulated prepares off — which this project already sets `ATTR_EMULATE_PREPARES => false`). The current code would break silently if someone removed the cast or changed the variable source.

## N+1 attendance status check in alumnos.php

```php
foreach ($alumnos as $alumno) {
    $stmt2 = $pdo->prepare("SELECT tipo FROM asistencias WHERE matricula_alumno = :mat AND fecha = :fecha ORDER BY hora DESC LIMIT 1");
    $stmt2->execute(['mat' => $alumno['matricula'], 'fecha' => $hoy]);
    $ultima = $stmt2->fetch();
    $estados[$alumno['matricula']] = $ultima ? $ultima['tipo'] : null;
}
```

With 15 students per page this produces 15 extra queries. At school scale with hundreds of students (or if someone changes the pagination to show all), this becomes a real bottleneck. A single LEFT JOIN with a subquery selecting `MAX(hora)` per student would eliminate this entirely.

## Missing schema definitions

The `dispositivos.php` page queries `dispositivos_padres` (columns: `id`, `matricula_alumno`, `token_fcm`, `fecha_registro`). The `usuarios.php` page queries `usuarios` (columns: `id_usuario`, `username`, `password_admin`, `nombre_completo`, `rol`, `ultimo_acceso`). Neither table appears in `database_structure.sql`. The schema file defines a `tokens_fcm` table instead, with different column names (`token` instead of `token_fcm`, includes `activo` flag). This is a mismatch: the admin panel references a table that doesn't exist in the official schema.

## Role escalation via usuarios.php

The page checks `$_SESSION['usuario_autenticado']` but not `$_SESSION['usuario_rol']`. A user with role "Vigilante" can navigate to `admin/usuarios.php` and create a new user with role "Admin", or change their own role by editing their record. The self-delete prevention doesn't extend to self-promotion.

## Dashboard "en plantel" query performance

```sql
SELECT COUNT(DISTINCT a1.matricula_alumno) as total
FROM asistencias a1
WHERE a1.fecha = :fecha AND a1.tipo = 'Entrada'
AND NOT EXISTS (
    SELECT 1 FROM asistencias a2
    WHERE a2.matricula_alumno = a1.matricula_alumno
    AND a2.fecha = a1.fecha AND a2.tipo = 'Salida'
    AND a2.hora > a1.hora
)
```

This correlated subquery checks every entry record against all exit records for the same student. With the existing `idx_matricula_fecha` index it won't table-scan, but the algorithmic cost grows with the number of entry/exit pairs per student per day. A student who enters and exits multiple times (forgot something, came back) multiplies the work. The view `v_ultimo_estatus_alumnos` already exists in the schema and solves this differently — the dashboard could use it instead.
